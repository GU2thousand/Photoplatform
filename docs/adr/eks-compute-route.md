# ADR: an independent EKS compute route

Date: 2026-09-28. Status: implemented deployment option; AWS activation is pending account inventory and acceptance evidence.

The existing infrastructure root mixes data services, ECR, ECS compute and the production ALB. Removing its ECS module would remove repositories as well as compute. The new EKS roots therefore reference existing resources by ID/ARN and leave every existing state address intact. There is no automatic ECS shutdown, data-service migration or production DNS switch.

The first target is `infra/environments/eks-dev`, an independent cluster named `photoplatform-eks-dev`, with namespace `photoplatform-dev`. `eks-prod` uses a separate cluster, namespace, state key, deploy role and secret allowlists. A new environment needs its own database, broker users, S3 prefix, frontend/API domains and budget; reusing a production VPC does not authorize reusing production data credentials. The original `infra/environments/dev` or `prod` state remains the only owner of its VPC, data services, CloudFront and ECR.

Use Helm as the application delivery source. Terraform owns cluster/node IAM, access entries, managed EKS add-ons, encryption, cluster logs, dedicated security groups and three inbound dependency grants. A platform administrator runs the pinned bootstrap for the load balancer controller, file-only Secrets CSI provider, metrics-server, namespace and restricted release RBAC. Helm owns application Deployments, Services, probes, configuration, file Secret mounts, Jobs, ingress and application policy. AWS Load Balancer Controller owns the EKS ALB/target groups/listeners. Terraform owns only that ALB's explicit security group. Existing ECS ALB resources and DNS remain separate.

Start with private managed EC2 AL2023 x86_64 CPU nodes and a separate ML pool with a scheduling taint. The initial application pool has two nodes; the ML pool has zero desired nodes until explicitly enabled. The cluster API has no public endpoint. A runner inside the VPC or connected network is mandatory, including for first bootstrap. Fargate, GPU, Kafka, in-cluster PostgreSQL/RabbitMQ, Argo CD and a shared RWO ML cache are outside this route.

The baseline is EKS 1.36, which the [AWS version lifecycle](https://docs.aws.amazon.com/eks/latest/userguide/kubernetes-versions.html) lists in standard support. Provider 6.66.0 is pinned by lock files. The AL2023 AMI release and managed add-on builds are mandatory explicit regional inputs: absent AWS inventory, no claim of regional compatibility is made. Controller/CSI/metrics versions and upstream checksums live in `deploy/eks-platform/versions.json`. Version upgrades change these contracts together and undergo a new plan, rendered-manifest check and dev rollout.

EKS adds a paid control plane, EC2 capacity, node patching, controllers, CNI policy and Kubernetes operational work. ECS remains simpler for the existing small workload. Independent deployment and workload resource isolation are the reasons to offer EKS; improved throughput, lower costs and operational simplicity have not been measured. The P0 budget and runner checks in [prerequisites](../kubernetes/prerequisites.md) are deployment gates.

Activation requires a reviewed plan that does not replace/delete existing data/ECR/ECS resources, live identity/network negative checks, a finite successful migration Job, new-digest rollout, business acceptance and rollback evidence. Only then can this be described as cloud validated. A public production endpoint and an actual separately recorded cutover are required before claiming production operation.
