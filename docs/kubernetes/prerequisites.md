# EKS deployment prerequisites

Repository validation does not create a cloud environment. Fill and retain [resource inventory](resource-inventory.md), a cost estimate and the final Terraform plan before activation. If AWS identity, a private runner, dependency inventory or regional version pins are missing, AWS deployment/acceptance is blocked even when local checks pass.

1. Pin the intended account and region with `aws sts get-caller-identity`; confirm the account equals `expected_account_id` and available credentials belong to the approved platform role. Before provisioning, run the read-only identity check below with that role; before application release use the environment's restricted release role. Do not use a developer's accidental default account. Record the repository SHA, the adopted SILO image digest and a successful Verify run for the final adopted main SHA.
2. Identify the existing state owner/backend key/serial for every shared resource. Back up the state securely, and use the additive original-root outputs to retrieve VPC, public/private subnet IDs, ECR ARNs, OIDC provider and bucket/distribution ARNs. Apply only an output refresh to the original root if needed; do not alter its compute or data resources. Reject overlap between `eks-dev` and `eks-prod` state keys.
3. Confirm private subnets span two AZs, have spare IPs for node/Pod ENIs plus rollout surge, have DNS support, and cannot assign public addresses. Inspect route tables: private subnet public-address flags alone do not prove route isolation. Verify HTTPS access through approved NAT or VPC endpoints for ECR API/DKR, S3, Secrets Manager, EKS, EKS Auth, STS as needed and telemetry; add endpoint SG ingress from node SG through the owning network state. EKS Pod Identity requires EKS Auth connectivity. Inspect RDS/MQ private placement and public-access flags, backups/PITR, TLS CA and engine limits.
4. Supply an existing VPC deployment runner SG and a named admin IAM role. Both provisioning/bootstrap and application release need DNS plus private API connectivity. A default GitHub-hosted runner cannot reach this private API. Use the configured self-hosted runner group or a controlled ephemeral VPC runner. Authenticate with GitHub OIDC or a short-lived AWS platform session; no long-lived access keys in GitHub.
5. Create separate restricted DB runtime/migrator users and MQ runtime/monitor users. A privileged one-time `CREATE EXTENSION vector` operation is performed by a platform administrator, not the migration Job. Store only exact runtime Secret ARNs in deployment inputs. Supply the forbidden RDS/MQ admin Secret ARNs and separate encoder-token Secret; do not give the encoder an application JWT/private-key Secret.
6. Prepare dedicated API dev/prod DNS names and same-region ACM certificates for the controller ALB. Confirm real frontend CORS/cookie origins and media signed-hostnames. Do not repoint the existing ECS domain during dev validation.
7. Approve the monthly cost envelope, maximum replicas/nodes and RDS connection headroom. ML starts disabled. Configure GitHub protected environments `eks-dev` and `eks-prod`; production requires named reviewers. The application release role cannot provision or destroy infrastructure, and the release flow must not execute Terraform apply.
8. Lock the cluster, AMI and add-on versions from the actual region. The reviewed cluster baseline is `1.36`; `addon_versions` and `node_ami_release_version` have no automatic latest fallback. Save the following read-only responses as evidence, select compatible Linux/x86_64/EC2 builds, and copy the exact strings into a local tfvars file:

The identity check needs only three explicit target values, so it can run before an EKS cluster, fixture tokens or deployment variables exist. Authenticate with the approved short-lived role session first, then set `EXPECTED_AWS_ACCOUNT_ID`, `AWS_REGION` and `AWS_ROLE_ARN` to the reviewed account, region and full IAM role ARN. Run from the repository root:

```sh
python3 scripts/deploy/eks_deploy.py identity
```

It performs only `sts get-caller-identity` with the explicit region, returns nonzero for the wrong account, an IAM user/root identity, an unexpected assumed-role name or invalid credentials, and writes `deployment-results/aws-identity.json`, replacing stale success evidence even when configuration is missing. IAM role paths are accepted: [AWS distinguishes the IAM role ARN with its path from the STS session ARN with its role name](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_identifiers.html). The report contains role/account metadata and timestamp, never credential values or raw AWS error output. Archive it with the other A0 evidence. A pass establishes the caller account and role name only; it does not confirm the configured IAM path, OIDC source, permissions, budget, state ownership, regional availability, network access or any deployment/acceptance gate. Every EKS release stage repeats the live identity check before cluster access or mutation. The existing `preflight` command validates release configuration without contacting AWS; it does not establish caller identity.

```sh
aws eks describe-cluster-versions --region us-east-1
aws eks describe-addon-versions --region us-east-1 --kubernetes-version 1.36 --addon-name vpc-cni
aws eks describe-addon-versions --region us-east-1 --kubernetes-version 1.36 --addon-name coredns
aws eks describe-addon-versions --region us-east-1 --kubernetes-version 1.36 --addon-name kube-proxy
aws eks describe-addon-versions --region us-east-1 --kubernetes-version 1.36 --addon-name eks-pod-identity-agent
aws ssm get-parameter --region us-east-1 --name /aws/service/eks/optimized-ami/1.36/amazon-linux-2023/x86_64/standard/recommended/release_version
```

These commands are examples for the selected region; replace `us-east-1` consistently. Confirm each add-on's configuration schema with `describe-addon-configuration`, especially `enableNetworkPolicy` and `NETWORK_POLICY_ENFORCING_MODE`. Record the EKS AL2023 image ID corresponding to the release version and check instance-type availability/quotas. [AWS's version lifecycle](https://docs.aws.amazon.com/eks/latest/userguide/kubernetes-versions.html) and [CNI policy guidance](https://docs.aws.amazon.com/eks/latest/userguide/cni-network-policy-configure.html) are the supported matrices; no regional API check has been performed by the repository fixtures.

The default app pool is two on-demand `m7i.large` nodes and the optional ML pool has zero desired nodes. At 730 hours/month, the [EKS standard-support control plane](https://aws.amazon.com/eks/pricing/) alone is $73. The [ALB pricing example for US East](https://aws.amazon.com/elasticloadbalancing/pricing/) is $0.0225/hour plus $0.008/LCU-hour: $16.425/month before LCU usage. [Public IPv4](https://aws.amazon.com/vpc/pricing/) adds $0.005/address-hour; two addresses are $7.30/month if allocated for 730 hours. These illustrative fixed components total $96.725/month before nodes, EBS, ALB usage, NAT, data transfer, log/metric ingestion, KMS, data services, S3/CDN, endpoints, taxes or support. They are not a full deployment quote. A two-AZ ALB can allocate more addresses as it scales. Existing NAT costs must be counted as allocated/shared costs, not assumed free; the VPC NAT example is not a confirmed us-east-1 quote. Extended-support control-plane pricing is higher, and the module chooses standard support.

For the actual cost sheet record region, price retrieval date, node pool size/type/hours, per-node 50 GiB gp3 storage, NAT/endpoints per AZ, expected transfer/ALB LCUs/log retention, DB/MQ configuration, existing service allocation and maximum rollout/autoscaling envelope. If the dev data services do not exist, price them independently before approval. Reusing ECS dependencies while retaining ECS compute has additive cost. There is no approved budget or measured EKS performance in this implementation.

After pins/inventory are complete, initialize only the intended root and backend, generate and review a plan, then perform platform provisioning as a separate approved operation. Follow `infra/environments/eks-dev/README.md` and the platform bootstrap README. Only actual AWS rollout/acceptance evidence satisfies the online acceptance requirement.
