# Media workers in Compose, ECS and Kubernetes

The same consumer image runs in each environment. `STORAGE_PROVIDER=minio` keeps the local endpoint and path-style addressing; `STORAGE_PROVIDER=aws` uses the SDK credential chain and virtual-hosted S3 addressing. In AWS, no explicit `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`, or `STORAGE_ENDPOINT` is passed to boto3. ECS task roles and EKS Pod Identity use refreshable credentials. Standard AWS credential-chain inputs still work for a developer running the image outside those platforms.

| Setting | Compose | ECS |
| --- | --- | --- |
| Storage | `STORAGE_ENDPOINT`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY` | `STORAGE_PROVIDER=aws`, `STORAGE_BUCKET`, `STORAGE_REGION`, task role |
| Object prefix | `STORAGE_PREFIX=generate-cloud` | `STORAGE_PREFIX=` for `staging/` and `media/` at bucket root |
| Database | `DATABASE_URL` | `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD` |
| Database TLS | Local default `prefer` | `DATABASE_SSL_MODE=verify-full`; CA `/app/certs/global-bundle.pem` |
| RabbitMQ | `RABBITMQ_URL=amqp://…` | `RABBITMQ_HOST`, `RABBITMQ_PORT=5671`, `RABBITMQ_USER`, `RABBITMQ_PASSWORD`, `RABBITMQ_SSL_ENABLED=true` |
| Queues | `WORKER_QUEUES=media.process,media.delete` | Same; independent embedding worker uses `media.embed` |
| Traces | `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel:4318` | `http://127.0.0.1:4318` for an ADOT sidecar |

Passwords are passed as discrete fields, so characters such as `@`, `/`, `?`, and `%` do not need URI escaping. ECS injects values from Secrets Manager at task start; rotating a secret requires replacing the running task. No application code retrieves Secrets Manager secrets itself. The worker fails configuration checks if AWS database TLS is weaker than `verify-full` or AMQP is plaintext. AMQPS verifies both the certificate chain and hostname. A custom broker trust bundle can be set through `RABBITMQ_CA_FILE`.

Kubernetes CSI mounts are read explicitly through `DATABASE_URL_FILE`, `DATABASE_USER_FILE`, `DATABASE_PASSWORD_FILE`, `RABBITMQ_URL_FILE`, `RABBITMQ_USER_FILE`, `RABBITMQ_PASSWORD_FILE`, and `ENCODER_TOKEN_FILE` (host overrides and local storage credentials are also supported). `/app/start.sh` loads them once and `exec`s its command, preserving SIGTERM delivery. Missing, empty, multiline, or conflicting values fail startup without printing secret contents. Rotation needs a coordinated rollout; reconnects retain the startup snapshot. `RABBITMQ_CA_FILE` remains a certificate path. Images run as UID/GID 10001, support a read-only root filesystem, and place home/ML caches and health files under writable `/tmp`.

Database connection acquisition makes at most three attempts by default, with 1-second and 2-second delays and a 5-second per-attempt connect timeout. `DATABASE_CONNECT_ATTEMPTS` is bounded to 1–5. SQL statements have a 30-second timeout, configurable through `DATABASE_STATEMENT_TIMEOUT_MS`. A SQL transaction is never automatically replayed after an ambiguous failure. Durable claims, advisory locks, leases, and the API outbox watchdog own recovery. S3 calls have three total SDK attempts, a 5-second connect timeout, and a 30-second read timeout.

RabbitMQ heartbeats stay on the main I/O thread while a single executor thread processes images. Prefetch is one **per consumer**, compatible with quorum queues and RabbitMQ 4.3; global QoS is not used. With the default two queues, a task may hold two unacknowledged deliveries but executes one job at a time. All waiting Futures are tracked across disconnects. Reconnects use exponential delay capped at 30 seconds plus at most one second of jitter; retries continue while the process is alive, allowing a broker to recover after an extended outage.

On SIGTERM, the worker stops accepting work, cancels queued work that has not started, and gives its active job `WORKER_SHUTDOWN_GRACE_SECONDS` (default 100) to finish while continuing broker heartbeats. One absolute deadline starts when the signal arrives and includes broker cancellation, drain and connection close; a daemon deadline guard bounds blocked Pika RPCs. ECS has a 120-second stop timeout; Kubernetes starts with at least a 120-second worker termination grace. If the grace expires, the process exits without acknowledging incomplete work. The renewable database lease and outbox watchdog recover it. Delivery remains at least once.

Claims use `WORKER_LEASE_SECONDS=300` and renew every `WORKER_LEASE_RENEW_SECONDS=30` on the same dedicated PostgreSQL session holding the media advisory lock. Renewal is claim-token fenced and cannot revive an expired lease. Runtime transactions lock image before job and serialize against renewal. Session loss stops subsequent storage writes and metadata commits; this session never reconnects. Use a direct RDS connection, avoiding transaction-pooling proxies. TCP keepalives and a 15-second TCP user timeout bound network failures in supported libpq/Linux runtimes.

An already accepted S3 request can finish after session loss. Each attempt therefore writes under its own claim-token prefix and registers that prefix in `media_object_attempts` before any PUT. This prevents stale attempts from overwriting a newer claim's published objects. A separate daemon sweep runs every 60 seconds, with up to 100 due prefixes per run and a dedicated advisory-lock session. First checks and active/locked attempts defer one minute; referenced and successfully swept prefixes defer one hour. It preserves active claims and any prefix referenced by `media_variants`, removes all versions/delete markers from abandoned prefixes, and retains registry rows for later sweeps to catch late PUTs. Failed sweeps leave rows due. Hourly tombstone reconciliation continues cleaning deleted media. Registry rows are retained, so their growth and sweep capacity need monitoring. Runtime DB credentials need SELECT/INSERT/UPDATE access to the V6 table; no schema DDL or registry DELETE is required. Include one active-job session, one potential GC session, and bounded probe connections per worker in the RDS connection budget.

## Targeted failure injection

Only in a disposable test task, set both `DISPOSABLE_ENVIRONMENT=true` and `WORKER_FAULT_AFTER_S3_JOB_ID=<exact job UUID>`. After all variant writes and before the metadata transaction, this task exits with code 86. Run replacement workers **without** the override, or the same job will crash repeatedly. This is an explicit process-loss test; it does not weaken ordinary job behavior. The cloud failure runbook is in `docs/failure-testing.md`.

Hosted local Kubernetes tests can use filesystem barriers only with `STORAGE_PROVIDER=minio`, `DISPOSABLE_ENVIRONMENT=true`, `WORKER_TEST_HOOK_ENVIRONMENT=kubernetes-local` (or `local`), and `WORKER_TEST_HOOK_DIR=/tmp/kind-worker-barriers`. Any configured `WORKER_TEST_HOOK_*` variable fails AWS worker startup. A `before_write.block` or `after_write.block` file pauses the matching stage; use `media-<mediaId>.<stage>.block` to isolate a media item before its job exists. The worker writes `<jobId>.<stage>.observed.json`, `<jobId>.stored` after all PUTs, and `<jobId>.fenced.json` when the original lease/session is lost. Markers include job/claim/session/Pod fields; after-write object keys are mapped full storage keys. Ownership is checked every second while paused. Removing the block file or creating `<jobId>.release` / `<mediaId>.release` resumes processing. The default900-second timeout is bounded to1–1800 seconds. These hooks never execute supplied code or rewrite durable job status.

## Metrics and verification

The metrics endpoint stays on port 9100. The original processing, job-age, end-to-end and storage timing metrics remain. Additional counters measure successful storage payload bytes, failed storage operations, client database query/acquire latency and failures, open worker DB connections, broker connectivity, and reconnect failures. Successful transfers include retry traffic; they are not unique-image counts. Cancelled jobs are counted separately from completed jobs so they do not inflate throughput.

Run unit tests from the repository root:

```sh
PYTHONPATH=worker python -m unittest discover -s worker/tests -v
python -m unittest discover -s ops/cloudwatch/tests -v
```

These tests cover configuration, TLS, bounded acquisition, cancellation, ACK connection ownership, a virtual-clock task exceeding the original five-minute lease, session and claim loss, storage/metadata fencing, attempt cleanup, secret rotation, and encoder HTTP readiness without connecting to cloud services. Real long-running jobs, node drain, DB/MQ outages, RDS certificates, S3 races and model inference remain deployment acceptance tests; unit tests do not establish cloud throughput or recovery time.

Primary references: [Amazon MQ Python/Pika TLS](https://docs.aws.amazon.com/amazon-mq/latest/developer-guide/amazon-mq-rabbitmq-pika.html), [RabbitMQ 4.3 changes](https://docs.aws.amazon.com/amazon-mq/latest/developer-guide/rabbitmq-43.html), [RDS TLS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.SSL.html).

ECS readiness runs `python -m app.health` (10-second timeout, 30-second interval). A JSON timestamp in `/tmp` is refreshed only by the subscribed, connected broker I/O loop, even while an image job is running. A missing or >15-second-old heartbeat fails readiness. Each check additionally opens one short-lived database connection with a 3-second connect timeout and a 1-second `SELECT 1` statement timeout. Authentication or TLS failures in either dependency therefore prevent an ECS rolling deployment from considering the worker healthy. Broker disconnect, subscription cancellation, and shutdown remove readiness. The probe tests database connectivity, not every schema permission or S3 operation; cloud smoke tests still verify those contracts.

Kubernetes readiness uses `python -m app.health --mode readiness` with a 5-second probe timeout. Liveness uses `--mode live`: only the independent main-loop heartbeat (maximum age 180 seconds) and its PID are checked. This budget covers broker RPC failure detection across two heartbeat windows; configured broker heartbeat must be 5–60 seconds. The loop marks liveness between broker operations, reconnect waits and active-job waits, so external DB/MQ outages make the process unready without forcing restart. Readiness itself does not cancel RabbitMQ subscriptions; failed durable state saves NACK for redelivery while reconnect/backoff stays bounded.

The encoder exposes `/livez` while the model loads in a background thread. `/readyz` returns 503 until a finite, unit-normalized 512-dimensional text warmup passes, then 200 with its model version. Initialization failures remain unready and log only the exception class. `/encode` requires the shared bearer token, matches `modelVersion`, and returns 503 while cold. `/health` remains informational HTTP 200 for compatibility; deployment probes must use `/readyz`.

Only `clip-vit-b32-openai-v1` is supported. Encoder startup verifies the official OpenAI ViT-B/32 checkpoint against SHA256 `40d365715913c9da98579312b702a82c18be219cc2a73407c4526f58eba950af` before loading it. `CLIP_MODEL_PATH` can reference a preinstalled copy; otherwise the fixed official URL downloads atomically into `$XDG_CACHE_HOME/photoplatform-clip` (default `/tmp/cache/photoplatform-clip`). Each Pod needs its own writable cache. Relabeled model versions, replacement expected hashes, and tampered checkpoints fail readiness. Cold health reports the expected digest separately from verified loaded artifact evidence. `/metrics` on the internal encoder port exposes `encoder_model_ready{model_version=...}` and `encoder_model_version_mismatches_total`. Mocked checkpoint tests do not establish real model accuracy or inference performance.
